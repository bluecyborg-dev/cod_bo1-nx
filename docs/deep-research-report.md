# Performance Optimization Techniques for Switch Homebrew Vulkan

1. **Batch draws with multi-draw / instancing.** Collapse many small draw calls into one by using `VK_EXT_multi_draw` or GPU instancing. For example, `vkCmdDrawMultiEXT` can issue hundreds of draws in one call. This eliminates per-draw API overhead – TechOverflow shows that a scene of 500 objects requiring 500 calls can be reduced to 1 multi-draw call. In our case, grouping e.g. 4 objects per draw would cut ~75% of draw overhead.  In practice, replacing ~1000 draws (25–40 µs each ≈30 ms CPU) with ~250 multi-draw calls (~8 ms CPU total by rough scaling) could free ~20 ms per frame. *Measured vs estimate:* Multi-draw’s benefit comes from its specification; the CPU savings are estimated by scaling (no exact Switch numbers found). Implementing this requires enabling `VK_EXT_multi_draw` (NVK supports Vulkan 1.4 with `gl_DrawID` for per-object data) and modifying the translation layer to batch identical pipelines. Effort is moderate; risk is low if carefully validated. *Sources:* TechOverflow on VK_EXT_multi_draw, NVK Vulkan conformance.

2. **Cache/replay static draw state (“command capture”).** Avoid rebinding the same state every frame. For static world geometry, record binding commands once (shaders, buffers, descriptors) and replay them each frame.  Deko3D’s docs describe a “command capture” mode where binding calls are recorded into a buffer and replayed. Likewise, sorting draws by render target, shader, and descriptor set (highest-cost state changes first) minimizes costly pipeline switches.  In practice, if e.g. 200 of our draws use the same shader and textures, capturing that state once would avoid hundreds of binds per frame. *Measured vs estimate:* Deko3D docs note that repeatedly calling bind functions becomes “significant” CPU work; capture eliminates that overhead. We estimate saving several µs per static draw. Implementing this in NVK would mean using secondary command buffers or custom caching (risky/complex). Effort is high (engine restructuring) but payoff is large for static geometry.

3. **Lower render resolution / use dynamic scaling.** Reducing the internal framebuffer size cuts GPU load sharply.  Many Switch ports use dynamic resolution to maintain frame rate.  For example, *Wolfenstein II* on Switch varies from 720p down to 640×360 under load.  In our port, dropping from 960×544 to, say, 800×450 halves the pixel count; this roughly halves fragment processing time. *Measured vs estimate:* Wolfenstein’s case shows that reducing resolution keeps FPS up on Tegra. We estimate a ~2× speedup in GPU work at 50% pixel count. Implementation is easy (set a smaller render target or scale output) but at cost of blurrier image. This applies to NVK/Vulkan or can be implemented via NVK’s swapchain/viewport. *Sources:* Wolfenstein II analysis (dynamic res on Switch).

4. **Upgrade Mesa NVK / use push constants efficiently.** Use the latest Mesa NVK driver (≥26.x) to pick up recent optimizations.  Notably, Mesa 24.2’s NVK patch “only write draw parameters to CB0 when they change” and “inline constant buffer updates for CB0”. This means NVK now avoids rewriting push-constant data every draw. Also, Mesa 25.0 increased NVK push-constant space to 256 B (useful for batching per-draw data).  Experimentally, Phoronix reports that NVK performance improved in Mesa 26.2. *Expected gain:* If previously NVK updated uniforms each draw (~2–5 µs), skipping unchanged updates can save ~1 µs/draw or ~1 ms per 1000 draws. This is modest but free since it’s driver-side. Effort is low (use updated Mesa build). Also ensure pipeline caching is used (already done). *Sources:* Mesa 3D NVK relnotes, Phoronix on NVK speed-ups.

5. **Throttle CPU scheduling and optimize code layout.** Make the render thread highest priority and prevent busy-waits.  On Horizon OS, use `svcSetThreadPriority` (above 0x3B real-time) and `svcWaitSynchronization` instead of spins.  Ensure each thread is pinned/affined to one A57 core (and use 48 KB I-cache-friendly code paths). Large static code and 2 MB page mappings can reduce TLB misses. *Measured vs estimate:* No public numbers, but A57’s small I-cache means scattered code is slow. Applying cache-aligned code and using real-time threads could regain a few microseconds per syscall or context switch. Risk is low; effort is medium (requires testing). NVK docs note a `coherent` flag for Tegra maps (not directly our issue). *Sources:* NVK debug flags (hints at Tegra cache control); Deko3D suggests large allocations to reduce fragmentation (analogous advice).

6. **Profile and remove heavy effects.** Disable or simplify post-effects and particle systems.  Past ports (Wii U CoD) showed that large maps and many alpha/explosion effects crushed performance. For Black Ops, turn off nonessential shaders (bloom, motion blur, etc) via engine `dvar`s. *Measured vs estimate:* Digital Foundry found that “alpha effects and explosions impact performance more heavily” on weaker hardware. If we disable a few such passes, we might regain ~5–15 FPS in GPU-heavy scenes. Effort is low (engine config tweaks); risk is low to moderate (visual fidelity loss). *Sources:* CoD: Ghosts WiiU DF report (maps/particles hit FPS).

7. **Frame pacing and input smoothing.** At 20–30 FPS target, ensure proper vsync and minimal queuing. Use only 1–2 frames in flight to reduce latency. Vulkan’s `vkQueuePresent` and `vkAcquireNextImageKHR` should be timed at vsync intervals. While this doesn’t speed up rendering, it makes low FPS feel steadier. *Measured vs estimate:* Guidelines from game development imply fewer in-flight frames feel smoother at low frame rate (no public Switch doc available). This is low effort (engine present code) and can improve perceived smoothness. *Sources:* General Vulkan best practices (no direct citation).

8. **(If feasible) Consider deko3d.** As a last resort, rewrite the renderer in devkitPro’s NVN-like API (deko3d) to shave driver overhead. Deko3d’s lazy-command model and capture API can reduce binds. *Expected gain:* Uncertain. It could cut some ms off the render-thread by avoiding Vulkan’s validation layers, but effort is massive (full rewrite). *Sources:* Deko3D optimization docs for concept.

**Top 5 Action Items:**  
1. **Implement batched multi-draw.** Enable `VK_EXT_multi_draw` and change the translation layer to combine identical-draw calls (4+ objects per `vkCmdDrawMulti*EXT`). This should **cut CPU draw overhead by ~50–75%** and directly tackles our ~1000-draw load.  
2. **Capture and reuse static draw state.** Use a “command capture” approach (as in deko3d) to record constant bind sequences once. Then replay them each frame instead of rebinding. This eliminates redundant bind calls. Start by caching any unchanging sets (meshes, materials) and see a large reduction in state-binding time.  
3. **Update NVK/Mesa and enable push-constant optimizations.** Build with Mesa 26.x and use NVK’s latest features. This gives us the inline constant-buffer updates and avoids redundant writes. It’s a low-risk way to shave a few µs per draw. Ensure pipelines are prewarms and descriptor updates minimized.  
4. **Lower resolution / add dynamic resolution.** Modify the renderer to render at a lower or dynamic resolution under load. Based on Wolfenstein’s port, this can roughly double GPU performance in heavy scenes. Implement as a quick test (even fixed 800×450) to see immediate FPS gains.  
5. **Disable nonessential shaders/effects.** Use engine config variables to turn off costly effects (full-screen flares, heavy particles, etc.). DF’s CoD:Ghosts analysis showed these as common bottlenecks on Nintendo hardware. Disabling a few should yield a measurable frame rate bump with minimal coding.  

Each of these steps targets a concrete hotspot: draw-call overhead and state changes first (CPU-bound), then GPU load and system-level tweaks. Together they should substantially improve stability and help hit or approach 30 FPS on the Switch.
